# Мультисерверный Xray: RU-вход + зарубежные выходы

Руководство по построению отказоустойчивой, TSPU-стойкой и управляемой через API инфраструктуры.
Актуально на **июль 2026**.

**Область применения.** Личное и полулюбительское использование (10–100 пользователей: друзья, знакомые, семья). Всё описанное — стандартные open-source инструменты (Xray-core, nginx, Docker). Ответственность за соблюдение законодательства своей юрисдикции лежит на вас; перед развёртыванием оцените правовые риски, особенно в части российского узла.

## 1. Главный вывод исследования

В июне 2026 был реверс-инжинирен алгоритм текущей волны ограничений. Он представляет собой **цепочку условий, соединённых логическим И**. Достаточно нарушить **любое одно** звено — и ограничение не применяется вовсе.

```
                    ┌──────────────────────────────────────┐
   ClientHello ───▶ │ 1. IP сервера в «подозрительной»      │── нет ──▶ ПРОПУСК
                    │    подсети / AS?                      │
                    └───────────────┬──────────────────────┘
                                   да
                    ┌───────────────▼──────────────────────┐
                    │ 2. Фингерпринт «браузера»             │── нет ──▶ ПРОПУСК
                    │    подозрительный?                    │
                    │    (Chrome / Safari / iOS — да;        │
                    │     Firefox / Edge / OkHttp — пока нет)│
                    └───────────────┬──────────────────────┘
                                   да
                    ┌───────────────▼──────────────────────┐
                    │ 3. > 3 параллельных TLS-соединений    │── нет ──▶ ПРОПУСК
                    │    к серверу в рамках ОДНОГО SNI      │
                    │    за последние 60 сек?               │
                    └───────────────┬──────────────────────┘
                                   да
                            ЗАМОРОЗКА 120 сек
                                    │
                    смена фингерпринта во время заморозки
                                    ▼
                     ДОПОЛНИТЕЛЬНАЯ БЛОКИРОВКА 600 сек
                     (любой TLS, независимо от SNI и fp)
```

### Что это значит конкретно для вашей схемы

| Факт из исследования | Следствие для вас |
|---|---|
| Затронуты **целые подсети и AS, в том числе российских ДЦ** (Selectel, Яндекс.Облако, Cloud.ru) | Российский VPS сам по себе не защищает. Но **ваш IP в белых списках** — это ровно звено №1. Если подсеть не «подозрительная», алгоритм останавливается на первом шаге. Это ваш главный актив, его надо беречь. |
| Фингерпринты Firefox / Edge / Android OkHttp пока проходят у большинства операторов | `fingerprint: "chrome"` — **больше не безопасный дефолт**. Ставим `firefox`. |
| Порог — 3 параллельных TLS в рамках одного SNI | Нужен **мультиплексор**. XHTTP + `xmux.maxConnections: "2-3"` держит число TLS-соединений ниже порога детерминированно. |
| Смена SNI обнуляет контекст счётчика | Несколько `shortIds` и, при желании, несколько SNI-доноров дают дополнительный запас. |
| **Пустой SNI ограничение не вызывает** | Резервный вектор, но ломает Reality (ему SNI нужен). Используйте в fallback-профилях. |
| Ограничение не зависит от порта, версии TLS и HTTP | Перенос на 8443 не помогает. Не тратьте время. |
| Отдельно: поведенческий анализ после рукопожатия (слой 4 DPI) | Reality маскирует **установку** соединения, но не то, что течёт по нему дальше. Это закрывает XHTTP, разбивающий поток на нормальные HTTP-транзакции. |
| Для **зарубежных** провайдеров дополнительно действует `tcp 16-20` (aka `l4-25`): TCP-соединение замораживается после ~14–34 КБ, если IP сервера в подсети Hetzner / OVH / DO / AWS / Cloudflare | Решающий аргумент за схему «клиент видит только российский IP». Плюс более поздняя механика — whitelist по SNI **и** CIDR: обойти её, по формулировке первоисточника, «как правило требует промежуточного узла с IP из белого списка». Это буквально описание вашей RU-ноды. Подробно — в [`docs/multi-entry.md`](docs/multi-entry.md) |

**Вывод.** Правильная конфигурация ломает алгоритм в трёх точках одновременно: белый IP (звено 1) + firefox-фингерпринт (звено 2) + xmux-лимит соединений (звено 3). Это не «одна хитрость», а эшелонированная защита — если РКН ужесточит один параметр, остальные два продолжат работать.

## 2. Панель управления

Панель — **Remnawave** (обоснование выбора — [`DECISIONS.md`](DECISIONS.md), ADR-0001;
развёрнутое сравнение с 3x-ui/Marzban/Marzneshin — [`docs/panel-comparison.md`](docs/panel-comparison.md)).
Установка — §5.2.

Известные ограничения, которые стоит учитывать при эксплуатации:

- Один мейнтейнер проекта — bus factor = 1. Держите бэкапы БД и умейте поднять
  голый Xray без панели (конфиги для этого — в `configs/`).
- 2 ГБ RAM на панель, нет мульти-админа, mux задаётся через сырой конфиг ядра
  (в `configs/` он уже так и сделан), документация только на английском.

Если по своим причинам разворачиваете на 3x-ui вместо Remnawave — модель
управления там другая (пользователь привязан к inbound на конкретном сервере),
и потребуется собственный оркестратор поверх его API; заготовка — в
`api/xui_orchestrator.py`, подробности использования — в
[`docs/panel-comparison.md`](docs/panel-comparison.md).

Подписка может отдавать разный формат разным клиентам (обычный Xray JSON для
INCY и подобных, отдельный YAML для Clash/Mihomo) — это встроенная функция
Remnawave (Templates + Response Rules), не то, что нужно писать самим.
Подробности и готовый Mihomo-шаблон — [`docs/client-templates.md`](docs/client-templates.md).

       │ fp: firefox, xmux 2-3, xPaddingBytes 100-1000
       │
  ┌────┴─────┐
  │ Клиенты  │  Happ / v2rayNG / Streisand / NekoBox
  │ в РФ     │  подписка → https://sub.вашдомен/...
  └──────────┘

### Роли узлов

| Узел | Роль | Что на нём | Что НЕ на нём |
|---|---|---|---|
| **DE-panel** (отдельный VPS, 2 vCPU / 4 GB) | Управляющий контур | Remnawave Panel, Postgres, Sub Page, ваш API-сервис | Пользовательский трафик |
| **RU-VPS** | Единственная точка входа для клиентов | Remnanode (Xray), nginx self-steal, реальный сайт-донор | Панель, БД, ключи выходных нод в открытом виде |
| **FR / DE / NL / KZ** | Выходы | Remnanode (Xray), inbound только для транзита с RU | Прямые клиентские подключения (в норме) |

### Ключевые решения

Полное обоснование каждого пункта (что рассматривалось и почему отклонено) —
[`DECISIONS.md`](DECISIONS.md), ADR-0002 — ADR-0006.

1. **Клиенты подключаются только к российскому IP** — тоннель до нужной страны идёт транзитом с RU-ноды, ClientHello клиента границу не пересекает.
2. **На RU-ноде — Reality в режиме self-steal**, не с чужим SNI-донором:

   ```
   ваш домен  →  A-запись  →  ваш RU IP  →  ваш Let's Encrypt сертификат  →  ваш реальный nginx
   ```

3. **Транспорт — XHTTP** поверх Reality на обоих хопах (клиент→RU и RU→выход); используются оба слоя одновременно, не как альтернативы.
4. **`fingerprint: "firefox"`** во всех клиентских и транзитных профилях (не `chrome`/`safari`/`ios`/`random`). Резервный профиль на `edge` держать наготове.
5. **`xmux.maxConnections: "2-3"`, `maxConcurrency: 0`** на каждом клиентском профиле и на транзитных outbound'ах RU-ноды.

## 4. Транзит RU → выходы

Транзит между RU-нодой и выходами — **Xray outbound chain** (VLESS+XHTTP+Reality).
Обоснование выбора и рассмотренные альтернативы (WireGuard, AmneziaWG,
dokodemo-door) — [`DECISIONS.md`](DECISIONS.md), ADR-0007.

**AmneziaWG** остаётся независимым резервным контуром — План Б, уровень E (раздел 8).
Если Xray-контур ляжет целиком, у пользователей останется рабочий профиль на другом стеке.

Про CPU: двойное шифрование на RU-ноде при 100 пользователях — это порядка 2 vCPU при пиковом трафике ~200–300 Мбит/с. Берите RU-VPS с AES-NI (любой современный Xeon/EPYC), и упрётесь в канал раньше, чем в процессор.

## 5. Пошаговое развёртывание

### Порядок

```
1. DNS                 → A-записи для всех узлов
2. Все узлы            → scripts/00-hardening.sh
3. Панель (DE)         → scripts/10-panel-install.sh
4. Выходные ноды       → scripts/20-node-install.sh
5. RU-нода             → scripts/20-node-install.sh + scripts/30-selfsteal.sh
6. Ключи               → scripts/40-keygen.sh на каждом узле
7. Конфиги Xray        → configs/ready/ (через UI панели или напрямую)
8. Preflight           → scripts/50-preflight.sh — плейсхолдеры не забыты?
9. Проверка            → scripts/90-healthcheck.sh + docs/tspu-checklist.md
```

Шаги 2–5 для всех серверов сразу можно прогнать одной командой через
`scripts/deploy.sh` — см. §5.6.

### 5.0. DNS

| Запись | Куда | Проксирование CF |
|---|---|---|
| `vpn.вашдомен.ru` | RU-VPS IP | **Выключено** (серое облако) — Reality несовместим с проксированием |
| `sub.вашдомен.ru` | панель (DE) | Включено (оранжевое) — прячет IP панели |
| `panel.вашдомен.ru` | панель (DE) | Включено + Cloudflare Access |
| `fr.вашдомен.ru`, `de.…`, `nl.…`, `kz.…` | выходные IP | Выключено |

Клиентам отдаётся **домен, не IP.** Это даёт возможность сменить российский сервер за 5 минут правкой A-записи, если IP всё-таки сгорит.

### 5.1. Базовый hardening (все узлы)

```bash
curl -fsSL -o 00-hardening.sh https://ваш-репозиторий/scripts/00-hardening.sh
# либо скопируйте файл из этого комплекта
sudo bash 00-hardening.sh --role node --panel-ip <IP_ПАНЕЛИ> --ssh-port 22022
```

Скрипт делает: обновление системы, отключение парольного SSH, смена порта SSH, ufw с явным списком портов, fail2ban, включение BBR + fq, увеличение лимитов файловых дескрипторов, установка Docker, отключение IPv6 (если не используете), настройка `unattended-upgrades`.

### 5.2. Панель (немецкий VPS)

```bash
sudo bash 10-panel-install.sh --domain panel.вашдомен.ru --sub-domain sub.вашдомен.ru
```

После установки:

1. Откройте `https://panel.вашдомен.ru`, создайте суперадмина **сразу** (регистрация открыта до первого админа).
2. Настройте Cloudflare Access или Telegram OAuth поверх — панель не должна быть публично доступной.
3. `Settings → API Keys` → создайте ключ для вашего сервиса. Скоуп — минимально необходимый.
4. `Settings → Webhooks` → укажите endpoint вашего сервиса и секрет.

### 5.3. Выходные ноды (FR / DE / NL / KZ)

В панели: `Nodes → Management → +`, заполните имя и адрес, скопируйте сгенерированный `docker-compose.yml`.

На ноде:

```bash
sudo bash 20-node-install.sh --panel-ip <IP_ПАНЕЛИ> --node-port 2222
# вставьте docker-compose.yml из панели в /opt/remnanode/docker-compose.yml
cd /opt/remnanode && docker compose up -d
```

Firewall на выходной ноде:

```bash
ufw allow from <IP_ПАНЕЛИ> to any port 2222 proto tcp   # управление
ufw allow from <IP_RU_НОДЫ> to any port 443 proto tcp   # транзит — ТОЛЬКО с RU-ноды
```

Транзитный inbound выходной ноды не должен быть доступен из интернета вообще. Это и защита от сканеров, и от того, что кто-то начнёт ходить на выход напрямую и спалит его.

**Если на сервере уже работает что-то своё (например x-ui)** — не обязательно сносить: Remnanode встаёт рядом на отдельном порту. См. `ARCHITECTURE.md §7.1` и `DECISIONS.md` ADR-0014 — коротко:

```bash
sudo bash 00-hardening.sh --role node --panel-ip <IP_ПАНЕЛИ> \
     --exit-ips <IP_RU_НОДЫ> --transit-port 8443 --no-fw-reset
```

`--no-fw-reset` не трогает существующий firewall, `--transit-port` — порт, заведомо свободный на этом сервере (проверьте `ss -tlnp` заранее). Дальше применяется `configs/xray-exit-node.json` (не `-public`) с этим же портом на `transit-in`, и тем же портом — `out-*` в `xray-transit-outbound.json` на RU-ноде.

### 5.4. RU-нода: self-steal

Это самый важный шаг. Порядок именно такой:

```bash
sudo bash 30-selfsteal.sh --domain vpn.вашдомен.ru --email вы@почта
```

Что происходит:

1. nginx поднимается на `127.0.0.1:8443` (TLS) и `0.0.0.0:80` (для ACME-challenge).
2. certbot получает сертификат Let's Encrypt на `vpn.вашдомен.ru`.
3. В `/var/www/selfsteal` разворачивается **настоящий статический сайт** — не «Hello World», а осмысленный контент: лендинг, документация, портфолио. Скрипт кладёт шаблон, но **замените его на что-то правдоподобное и уникальное**.
4. Настраивается автообновление сертификата.

Затем ставится нода:

```bash
sudo bash 20-node-install.sh --panel-ip <IP_ПАНЕЛИ> --node-port 2222
```

И в панели для RU-ноды применяется конфиг из `configs/xray-ru-entry.json` — inbound с `realitySettings.dest: "127.0.0.1:8443"` и `serverNames: ["vpn.вашдомен.ru"]`.

**Проверка self-steal (обязательна, с внешнего хоста):**

```bash
curl -sSI https://vpn.вашдомен.ru/ | head -20
```

Должен вернуться нормальный HTTP-ответ вашего сайта с валидным сертификатом. Если получаете TLS-ошибку или обрыв — self-steal собран неправильно, и вы уязвимы к активному зондированию.

### 5.5. Транзит и маршрутизация

На RU-ноде применяется `configs/xray-transit-outbound.json`: outbound'ы `out-fr`, `out-de`, `out-nl`, `out-kz` плюс `direct` и `block`.

Правила маршрутизации на RU-ноде (в порядке приоритета):

| Приоритет | Правило | Действие | Зачем |
|---|---|---|---|
| 1 | `geoip:private` | `block` | Не даём ходить во внутреннюю сеть хостера |
| 2 | `protocol: bittorrent` | `block` | **Критично** — торренты с белого IP сожгут его репутацию и приведут к абузам |
| 3 | `geosite:category-gov-ru`, банки, госуслуги | `direct` | Российские сервисы блокируют зарубежные IP. Пусть идут напрямую с RU-ноды |
| 4 | по тегу пользователя / сквада | `out-fr` / `out-de` / `out-nl` / `out-kz` | Выбор страны |
| 5 | всё остальное | `out-de` (дефолт) | — |

Правило 3 — это ещё и мощная фича: у пользователя одновременно работают и заблокированные зарубежные сервисы, и российские банки. Обычный зарубежный VPN так не умеет.

### 5.6. Автоматизация: deploy.sh

Шаги 5.1–5.4 (везде, кроме шагов в UI панели) можно прогнать одной командой по всем серверам сразу:

```bash
cp scripts/deploy.conf.example scripts/deploy.conf   # заполнить своими значениями
bash scripts/deploy.sh --inventory scripts/deploy.conf --dry-run   # сначала так, без подключения
bash scripts/deploy.sh --inventory scripts/deploy.conf             # затем по-настоящему (спросит подтверждение)
```

Роли в инвентаре — `panel` / `ru-entry` / `exit-fresh` / `exit-coexist` (для сервера с уже работающим x-ui — см. §5.3). Формат — `scripts/deploy.conf.example`, подробности — `ARCHITECTURE.md §7.2`, обоснование выбора именно такого инструмента — `DECISIONS.md` ADR-0015.

`deploy.sh` **не** меняет SSH-порт и **не** делает шаги в UI панели (суперадмин, `Nodes → Management → +`, config-profile) — это остаётся руками между вызовами.

## 6. Защита «белого» IP

Ваш российский IP в белых списках — самый ценный и самый хрупкий элемент схемы. Потерять его = потерять всё преимущество. Правила:

### Технические

- **Торренты — заблокированы на уровне routing.** Не «не рекомендуем», а `protocol: bittorrent → block`. Одна абуза за раздачу — и IP уходит из белых списков.
- **Порт-скан и SMTP наружу — заблокированы.** Порт 25 закрыт на исходящие.
- **HWID-лимит устройств** в Remnawave: 3–5 устройств на пользователя. Это защита от расползания ключей.
- **Лимит трафика на пользователя.** Даже щедрый (500 ГБ/мес) отсекает того, кто решит качать через вас медиатеку.
- **Rate limit на подключения** — в скрипте hardening через `iptables -m connlimit`.
- **Не хостить панель и БД на этом же IP.** Если сервер изымут или скомпрометируют, база пользователей не должна там лежать.
- **Мониторинг соотношения in/out трафика.** У настоящего веб-сервера исходящий трафик сильно превышает входящий. Если у вас они примерно равны — профиль аномален для заявленного «сайта». Это не критично при self-steal (сайт-то настоящий), но за метрикой стоит следить.

### Организационные

- Раздавайте **ссылку на подписку**, а не сырой VLESS-URI. Так вы можете отозвать/поменять конфиг у конкретного человека.
- Ведите учёт: кому какой ключ. При утечке — понятно, чей.
- Никогда не публикуйте домен/IP в публичных чатах, каналах, на GitHub.
- Не используйте один домен для панели и для входной ноды.

### Быстрая эвакуация

Держите **заранее подготовленный второй RU-VPS** у другого провайдера, с уже настроенным nginx и сертификатом на второй домен. Если основной IP сгорит: меняете A-запись → пользователи переподключаются автоматически через подписку, без единого сообщения в чат. Стоимость — цена одного дешёвого VPS в месяц.

## 7. Управление через API

Готовые варианты **существуют, писать с нуля не надо** — но обёртку под свои процессы сделать полезно.

### Что даёт Remnawave из коробки

| Возможность | Как |
|---|---|
| REST API | Полная OpenAPI-спека: `https://docs.rw/api` |
| Официальный SDK | TypeScript SDK (`@remnawave/backend-contract`) |
| Вебхуки | События по пользователям и нодам → ваш endpoint |
| Telegram-бот | Встроенные уведомления + OAuth-авторизация |
| Готовые сообщества-решения | Каталог `awesome-remnawave`: боты, биллинги, панели статистики, автобэкапы |

Прежде чем писать своё — посмотрите `awesome-remnawave`. Скорее всего, ваш сценарий уже реализован.

### Заготовки в этом комплекте

- **`api/remnawave_client.py`** — асинхронный Python-клиент: пользователи (CRUD, продление, сброс трафика), ноды (статус, вкл/выкл), сквады, хосты, статистика, генерация ссылок подписки.
- **`api/webhook_server.py`** — FastAPI-приёмник вебхуков с проверкой HMAC-подписи и заготовками обработчиков (юзер исчерпал трафик, юзер истёк, нода упала).
- **`api/xui_orchestrator.py`** — на случай, если останетесь на 3x-ui: синхронизирует одного пользователя между N инсталляций 3x-ui через их API.

Типовые сценарии — в [`docs/api-automation.md`](docs/api-automation.md).

## 8. План Б и деградация

Правило: **ни одна сигнатура не должна класть всё сразу.** Стройте так, чтобы у каждого пользователя в подписке было несколько разнородных профилей.

| Уровень | Что | Когда включается |
|---|---|---|
| **A. Основной** | VLESS + XHTTP + Reality self-steal через RU-вход, fp `firefox` | Всегда |
| **B. Смена фингерпринта** | То же, но fp `edge` / `okhttp` | Если `firefox` попадёт в чёрный список |
| **C. Второй SNI / shortId** | Тот же узел, другой `shortId` и путь XHTTP | Смена SNI обнуляет контекст счётчика соединений |
| **C+. Вторые RU-врата** | Второй российский VPS с белым IP у другого провайдера | **Самое выгодное вложение в отказоустойчивость** — надёжнее любого прямого зарубежного входа |
| **D. Прямой выход** | VLESS + XHTTP + Reality напрямую на зарубежную ноду, минуя RU | Если ляжет RU-нода. Упирается в `tcp 16-20`: у части пользователей не заработает. См. [`docs/multi-entry.md`](docs/multi-entry.md) |
| **E. Другой стек** | AmneziaWG на отдельной зарубежной ноде | Если Xray-контур попадёт под блок целиком |

Remnawave позволяет отдать все профили **в одной подписке** — клиенты вроде Happ и v2rayNG сами переключаются по доступности. Пользователю ничего делать не надо, и вам не надо рассылать новые ключи в панике.

### Сигналы, что вас начали ловить

- Массовые жалобы «работает 30 секунд, потом виснет» → похоже на заморозку 120 сек, звено 3. Проверьте `xmux`.
- Не работает у одного оператора, работает у другого → региональный ТСПУ, ждите/меняйте fp.
- Перестало работать сразу у всех и полностью → скорее всего IP или подсеть. Эвакуация (раздел 6).
- Работает через мобильный интернет, не работает через домашний (или наоборот) → разные политики операторов, нормально.

## 9. Эксплуатация

### Регулярно

| Периодичность | Действие |
|---|---|
| Ежедневно | `scripts/90-healthcheck.sh` по cron → уведомление в Telegram при падении ноды |
| Еженедельно | Бэкап БД панели (`pg_dump`) в внешнее хранилище |
| Еженедельно | Проверка `dpi-checkers` / `dpi-ch` на предмет попадания ваших подсетей в «подозрительные» |
| При обновлении Xray | **Версии ядра на сервере и клиенте обязаны совпадать.** XHTTP в активной разработке; рассинхрон даёт неочевидные глюки без внятных ошибок. Обновляете сервер — предупреждайте пользователей |
| Ежемесячно | Ревизия списка пользователей: кто не заходил 60 дней — отключить |

### Чего категорически не делать

- Не обновляйте Xray на всех нодах одновременно. Сначала одна, сутки наблюдения, потом остальные.
- Не меняйте фингерпринт «на горячую» во время активной заморозки — получите блокировку на 600 секунд вместо 120.
- Не ставьте панель на российский VPS.
- Не используйте `fingerprint: "chrome"` в 2026.
- Не оставляйте порт ноды (2222) открытым в интернет.
