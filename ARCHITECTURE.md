# ARCHITECTURE.md

Техническое описание инфраструктуры: узлы, слои, протоколы, порты, поток
данных. Обоснование *почему* именно так — в [`DECISIONS.md`](DECISIONS.md).
Пошаговое развёртывание — в [`README.md`](README.md#5-пошаговое-развёртывание).

Актуально на июль 2026.

## 1. Обзор в одной схеме

```
┌──────────────────────────────────────────────────────────────────────┐
│  УПРАВЛЯЮЩИЙ КОНТУР (вне РФ, отдельный VPS — напр. Германия)         │
│                                                                       │
│   Remnawave Panel ── Postgres          Ваш сервис/бот                │
│   + Sub Page              ▲            (REST API + webhook receiver) │
│        │                  │                    ▲                     │
│        │ панель→нода,     └────────────────────┘                     │
│        │ порт 2222,                                                  │
│        │ только с IP панели                                          │
└────────┼───────────────────────────────────────────────────────────── ┘
         │
    ┌────┴──────┬───────────┬───────────┬──────────┐
    ▼            ▼           ▼           ▼          ▼
┌─────────┐  ┌────────┐  ┌────────┐  ┌────────┐ ┌────────┐
│ RU VPS  │  │  FR    │  │  DE    │  │  NL    │ │  KZ    │
│ «ВРАТА» │  │ exit   │  │ exit   │  │ exit   │ │ exit   │
│ белый IP│  └───▲────┘  └───▲────┘  └───▲────┘ └───▲────┘
│         │      │           │           │          │
│Remnanode│      └───────────┴───────────┴──────────┘
│+ nginx  │       ЗВЕНО 2: транзит (Xray outbound chain)
│selfsteal│       VLESS + XHTTP + Reality (сторонний SNI-донор)
└────▲────┘       xmux 2-3, fp: firefox
     │
     │ ЗВЕНО 1: клиентское подключение
     │ VLESS + XHTTP + Reality (self-steal, свой домен)
     │ fp: firefox, xmux 2-3, xPaddingBytes 100-1000
┌────┴─────┐
│ Клиенты  │  Happ / v2rayNG / Streisand / NekoBox
│  в РФ    │  подписка → https://sub.домен/...
└──────────┘
```

Два физически и организационно разделённых контура:

- **Управляющий** — панель, БД, автоматизация. Вне России. Ничего пользовательского
  не проксирует.
- **Контур передачи данных** — RU-вход + зарубежные выходы. Только Remnanode
  (Xray) и nginx self-steal. Никакой базы пользователей.

## 2. Роли узлов

| Узел | Роль | Что на нём | Чего на нём НЕТ |
|---|---|---|---|
| **DE-panel** (2 vCPU/4 GB) | Управляющий контур | Remnawave Panel, Postgres, Sub Page, свой API-сервис/вебхук-приёмник | Пользовательский трафик |
| **RU-VPS** | Единственная точка входа для клиентов | Remnanode (Xray), nginx self-steal, реальный сайт-донор | Панель, БД, ключи выходных нод в открытом виде |
| **FR / DE / NL / KZ** | Выходы | Remnanode (Xray), inbound для транзита с RU (+опционально публичный вход) | Прямые клиентские подключения в штатном режиме |

Ноды продолжают обслуживать трафик при падении панели (архитектурное свойство
Remnawave, см. [`docs/panel-comparison.md`](docs/panel-comparison.md)) — авария
управляющего контура не рвёт уже установленные соединения.

## 3. Протокольный стек

Два независимых слоя защиты, применяемых на обоих хопах (клиент→RU и RU→выход):

| Слой | Что делает | Где закрывает детекцию |
|---|---|---|
| **Reality** | Маскирует TLS-рукопожатие под настоящий сайт-донор | Активное зондирование (слой 3 DPI) — на рукопожатии |
| **XHTTP** | Разбивает поток на HTTP-транзакции вместо постоянного двунаправленного потока | Поведенческий анализ (слой 4 DPI) — после рукопожатия |

Различие между хопами — способ получения донора:

| Хоп | Reality-режим | Донор | Почему так |
|---|---|---|---|
| Клиент → RU-нода | **Self-steal** | Собственный домен, свой сертификат Let's Encrypt, свой реальный сайт | На российском хостинге чужой SNI-донор даёт несоответствие SNI↔ASN (сертификат Microsoft, IP российского провайдера) — детектируемо |
| RU-нода → выход | **Классический Reality** | Чужой глобальный CDN-домен (`www.microsoft.com`, `www.twitch.tv`, `github.com`) | Выходная нода стоит в Европе — ASN-несоответствие несущественно, PoP донора есть везде |

Общие анти-детект параметры на обоих хопах:

| Параметр | Значение | Звено алгоритма, которое ломает |
|---|---|---|
| `fingerprint` | `firefox` (не `chrome`/`safari`/`ios`/`random`) | Звено 2 — фингерпринт браузера |
| `xmux.maxConnections` | `"2-3"`, `maxConcurrency: 0` | Звено 3 — число параллельных TLS к одному SNI |
| `xPaddingBytes` | `"100-1000"` | Поведенческий ML-классификатор (слой 4) |
| Белый IP RU-ноды | — | Звено 1 — подозрительность подсети/AS |

Подробный разбор алгоритма ограничений — README §1; методика проверки каждого
пункта — [`docs/tspu-checklist.md`](docs/tspu-checklist.md).

## 4. Карта портов

| Порт | Узел | Протокол/назначение | Кто может подключаться |
|---|---|---|---|
| 443 | RU-нода | VLESS+XHTTP+Reality, клиентский вход | Весь интернет |
| 127.0.0.1:8443 | RU-нода | nginx self-steal (dest для Reality) | Только сам Xray (dest) |
| 8443 | Выходная нода (все 6: FR/KZ/FI/NL/DE/MD) | VLESS+XHTTP+Reality, транзит с RU (`transit-in-*`) | Только IP RU-ноды (firewall) |
| 443 | Выходная нода (все 6, **кроме FR — см. ниже**) | VLESS+XHTTP+Reality, прямой клиентский вход (Direct) — squad'ы `Tavrida`/`VIP Users`/`Standard Access` (см. §10) | Весь интернет |
| 2083 | Выходная нода **FR only** | То же самое (Direct), но на 443 у FR порт воспроизводимо не отвечает на TLS-уровне (ADR-0018, root cause не найден) — 2083 как рабочее исключение | Весь интернет |
| 9443 | Выходная нода (все 6) | VLESS+TCP+Reality, резервный транспорт без XHTTP (Reserve/RAW) — те же squad'ы, что и Direct | Весь интернет |
| 2222 | Любая нода | Управление от панели (Remnanode API) | Только IP панели |
| 127.0.0.1:10085 | Любая нода | Xray API (HandlerService/StatsService/LoggerService) | Только localhost |
| 443/3000 | Панель | Remnawave Panel (за nginx reverse proxy) | Ограничено allow-list/Cloudflare Access |
| 3010 | Панель | Sub Page (страница подписки) | Весь интернет (публичная) |
| 80 | Панель, RU-нода, выходные ноды | ACME challenge + редирект на 443 | Весь интернет |
| 22/22, `--ssh-port` | Все узлы | SSH, только по ключу | Ограничено (fail2ban) |
| 25/465/587 (исходящие) | RU-нода, выходные ноды | SMTP | **Заблокировано** (гигиена белого IP) |

## 5. Маршрутизация на RU-ноде

Приоритет правил в `xray-transit-outbound.json` (полный список — сам файл;
чеклист для проверки — `docs/tspu-checklist.md`):

1. Xray API (`api-in`) → локально
2. `geoip:private` → block (не пускать во внутреннюю сеть хостера)
3. `protocol: bittorrent` → block (защита белого IP)
4. Порты 25/465/587 → block (защита от спам-абуз)
5. `geosite:category-ads-all` → block (экономия трафика)
6. Российские домены/банки/госуслуги → `direct` (обходят тоннель — иначе увидят зарубежный IP и заблокируют вход)
7. `geoip:ru` → `direct`
8. По пользователю/сквад-тегу → конкретный `out-kz`/`out-fi`/`out-nl`/`out-de`/`out-md`
9. Всё остальное → `out-fr` (дефолт — единственное catch-all правило; остальные
   `out-*` сейчас достижимы только через явный маршрут по пользователю/squad,
   которого пока нет — см. `memory` проекта)

Балансировщик `eu-pool` (leastPing по `out-de`/`out-fr`/`out-nl`) определён, но
не подключён к правилам по умолчанию — опция для тех, кто предпочитает
автовыбор выхода вместо ручного назначения по пользователю.

## 6. Мультивход и деградация (План Б)

Полное обоснование и ловушки — [`docs/multi-entry.md`](docs/multi-entry.md).
Лестница приоритетов (не равноправный набор входов):

| Уровень | Что | Когда включается |
|---|---|---|
| A. Основной | RU-вход, self-steal, fp `firefox` | Всегда |
| B. Смена фингерпринта | То же, fp `edge`/`okhttp` | `firefox` попал в чёрный список |
| C. Второй SNI/shortId | Тот же узел, другой `shortId`/путь | Смена SNI сбрасывает счётчик звена 3 |
| C+. Вторые RU-врата | Второй RU-VPS, другой провайдер, тоже белый IP | Надёжнее любого прямого зарубежного входа — приоритетное вложение |
| D. Прямой выход | VLESS+XHTTP+Reality напрямую на зарубежную ноду | RU-нода недоступна; упирается в `tcp 16-20` — работает не у всех |
| E. Другой стек | AmneziaWG на отдельной зарубежной ноде | Xray-контур заблокирован целиком |

Уровень D реализован не только как аварийная деградация, но и как постоянный
второй тег доступа — squad `VIP-Direct` (§10): выбранным пользователям прямой
выход доступен параллельно с RU-вратами, а не только когда те недоступны.
Ограничение `tcp 16-20` при этом никуда не девается — включать этот доступ
людям стоит с тем же пониманием ограничений, что описано в
[`docs/multi-entry.md`](docs/multi-entry.md).

Ключевое: клиентский автовыбор по `leastPing` систематически выбирает *худший*
узел при активном `tcp 16-20` (быстрый пинг ≠ работоспособность под нагрузкой на
объёме >14–34 КБ) — см. `docs/multi-entry.md §4` и `scripts/60-entry-test.sh`,
который тестирует именно объём, а не рукопожатие.

## 7. Конвейер развёртывания

Скрипты пронумерованы в порядке применения:

| Скрипт | Роль/узел | Что делает | Ключевые побочные эффекты |
|---|---|---|---|
| `00-hardening.sh --role panel\|node [--ru-entry] [--exit-ips ...] [--transit-port] [--no-fw-reset]` | Все узлы | SSH только по ключу + смена порта, ufw (deny-by-default), fail2ban, BBR+fq, лимиты FD, Docker, блок исходящего SMTP, автообновления, swap | Роль `node --ru-entry` открывает 443 всем; `node` без флага — только с `--exit-ips`. `--transit-port`/`--no-fw-reset` — режим сосуществования с уже работающим сервисом (см. §7.1) |
| `10-panel-install.sh --domain --sub-domain --email` | DE-panel | Remnawave Panel + Postgres + Sub Page (Docker Compose), nginx reverse proxy, сертификат, ежедневный `pg_dump`-бэкап в 04:17 UTC | Секреты в `/opt/remnawave/.env` (chmod 600) — не коммитить |
| `20-node-install.sh --panel-ip --node-port` | Любая нода | Remnanode (Docker), geoip/geosite (еженедельное обновление по понедельникам), firewall панель→нода | Требует вставки `SECRET_KEY` из сгенерированного панелью docker-compose.yml (Nodes → нода → «Copy docker-compose.yml») вручную |
| `30-selfsteal.sh --domain --email` | RU-нода (+ опционально зарубежные при public-входе) | nginx на `127.0.0.1:8443`, Let's Encrypt, шаблон реального сайта в `/var/www/selfsteal`, автообновление сертификата | **Обязательно заменить шаблонный контент** — одинаковый контент на разных IP сам по себе сигнатура |
| `40-keygen.sh --name --sni [--selfsteal] [--port]` | Любая нода (запуск при подготовке конфига) | Генерирует Reality keypair, UUID, shortId'ы, правдоподобный XHTTP-путь; печатает готовые фрагменты server/client конфига и `vless://`-ссылку | Ничего не пишет на диск — только stdout. `--port` — если транзитный порт не 443 (см. §7.1) |
| `50-preflight.sh [файлы]` | Локально, перед выкаткой | Валидность JSON, незаменённые плейсхолдеры, fingerprint, парность xmux, блок торрентов/private, кросс-сверка `transit-in` ↔ `out-*` | Не трогает серверы — чисто статический анализ конфигов |
| `60-entry-test.sh --hosts "..." [--proxy host:port]` | Запускать **из России**, не с сервера | Проверка входов на объёме (10 КБ → 5 МБ) — ловит `tcp 16-20`, которое рукопожатие не показывает | Не изменяет инфраструктуру, только измеряет |
| `90-healthcheck.sh --config /opt/healthcheck.conf [--notify]` | Периодически (cron, раз в 10 мин) | Self-steal жив, сертификат не истекает, CN совпадает, выходные ноды на связи, версии Xray едины, ресурсы узла, гигиена белого IP; шлёт в Telegram при `--notify` | Только чтение состояния, без изменений |
| `deploy.sh --inventory FILE [--dry-run\|--yes] [--only NAME]` | Локально, оркестрирует остальные | Прогоняет по SSH `00`/`10`/`20`/`30` в нужном порядке на всех серверах инвентаря сразу (формат — `deploy.conf.example`) | Не меняет SSH-порт, не трогает шаги в UI панели — см. §7.2 и ADR-0015 |

Порядок в README §5 (`5.0`…`5.5`, затем `50`→`90`) — авторитетная
последовательность для первого разворачивания с нуля.

Все скрипты `00`–`90` писаны под Debian/Ubuntu (`apt`/`ufw`/`systemd`) и не
отработают на Alpine без адаптации — для узла на Alpine Linux используется
[`docs/alpine-node-setup.md`](docs/alpine-node-setup.md) (тот же смысл, но
`apk`/OpenRC, ручной пошаговый вариант, не отдельный автоматизированный
скрипт).

### 7.1. Сосуществование с уже работающим сервисом на выходной ноде

Если на зарубежном сервере уже работает что-то своё (например x-ui), полная
замена — не единственный путь (обоснование — `DECISIONS.md` ADR-0014):

- `00-hardening.sh ... --transit-port <port> --no-fw-reset` — не сбрасывает
  firewall и не занимает порт 443 для транзита.
- Используется `xray-exit-node.json` (только транзит), не `-public` вариант —
  публичный вход на этом сервере и так закрывает существующий сервис.
- `40-keygen.sh ... --port <port>` — генерирует конфиг под тот же порт.
- Порт обязан совпадать с `out-*.settings.vnext[].port` соответствующей записи
  в `xray-transit-outbound.json` на RU-ноде — тот же класс рассинхрона, что и
  в ADR-0013, и та же проверка (`50-preflight.sh`) его ловит.
- Порт должен быть заранее проверен как свободный (`ss -tlnp` на сервере) —
  автоматически это не проверяется.

### 7.2. Автоматизация через deploy.sh

`scripts/deploy.sh` (ADR-0015) — не новый механизм развёртывания, а обёртка
над тем же самым конвейером: по инвентарю (`name|role|host|user|port|extra`,
роли `panel`/`ru-entry`/`exit-fresh`/`exit-coexist`) вызывает по SSH ровно те
же скрипты с нужными для роли флагами. Осознанно не автоматизирует смену
SSH-порта и шаги в UI панели (суперадмин, привязка ноды, config-profile) —
это остаётся ручными шагами между вызовами `deploy.sh` и после него.

## 8. Управляющий/автоматизационный слой

| Компонент | Файл | Назначение |
|---|---|---|
| Асинхронный клиент Remnawave API | `api/remnawave_client.py` | CRUD пользователей, ноды, сквады, хосты, статистика, готовые сценарии (`onboard_friend`, `cleanup_inactive`, `verify_routes`) |
| Приёмник вебхуков | `api/webhook_server.py` | FastAPI, HMAC-проверка подписи, обработчики событий (трафик исчерпан, нода упала/восстановилась, юзер истёк) → уведомления в Telegram |
| Оркестратор 3x-ui | `api/xui_orchestrator.py` | Запасной путь, если решили остаться на 3x-ui вместо Remnawave — веерные операции по N панелям + обязательный `reconcile()` |

Панель Remnawave — источник истины по пользователям/нодам; собственный сервис
(`api/`) работает **поверх** её API, не вместо него. Каталог `awesome-remnawave`
(упомянут в `docs/api-automation.md`) стоит проверять до написания нового кода —
типовые сценарии (боты, биллинг, бэкапы, мониторинг) там уже могут быть готовы.

## 9. Данные и их время жизни

- `"access": "none"`, `dnsLog: false` в конфигах Xray — посещённые домены и
  IP-адреса пользователей принципиально не логируются.
- Логи вебхук-приёмника и панели не должны содержать содержимое трафика,
  посещённые домены, IP пользователей дольше необходимого (`docs/api-automation.md §8`).
- Реальные ключи/UUID/домены живут только на развёрнутых серверах и в
  `.env`-файлах (`chmod 600`) — не в этом репозитории и не в git-истории.

## 10. Уровни доступа (Remnawave Internal Squads)

Remnawave подставляет пользователю в подписку inbound'ы **со всех** squad'ов,
в которых он состоит — это и есть механизм многоуровневого доступа, без
дублирования пользователей. Структура ниже — ADR-0017, заменяет более
раннюю двухуровневую схему из ADR-0016.

Две независимые оси доступа свёрнуты в три squad'а:
- **Доверие** — узкий круг (видит всё, включая лимитные ноды) vs обычные
  пользователи (только безлимитные ноды).
- **Лимит трафика хостинга** — FR и DE ограничены провайдером (4ТБ/мес),
  остальные четыре ноды безлимитны. Ограничение только по доступу (squad),
  не техническим счётчиком Remnawave — осознанный выбор (ADR-0017).

| Squad | Инбаунды | Кому |
|---|---|---|
| `Tavrida` | все 12 `client-in-*`/`raw-in-*` (все 6 нод: FR/KZ/FI/NL/DE/MD), **без** RU-Gate | Узкий круг №1 |
| `VIP Users` | те же 12 + `vless-xhttp-reality-in` (RU-Gate, порт 443 на ru-entry) | Узкий круг №2 (плюс вход через РФ) |
| `Standard Access` | `client-in-*`/`raw-in-*` только безлимитных нод (KZ/FI/NL/MD) — без RU-Gate, без FR/DE | Все остальные обычные пользователи |
| `Transit-FR`/`Transit-KZ`/`Transit-FI`/`Transit-NL`/`Transit-DE`/`Transit-MD` | По одному `transit-in-*` на squad | Служебные пользователи (`svc-transit-*`) — see §7, не для людей |

`Tavrida` и `VIP Users` оба видят вообще все ноды — единственная разница
между ними в том, что `VIP Users` дополнительно даёт RU-Gate, а `Tavrida`
нет (осознанное разделение, не техническое ограничение).

**Устройство `client-in-*`/`raw-in-*` (порты 443/9443, §4).** Тот же
классический Reality-донор, что уже используется транзитным `transit-in-*`
на этой же ноде (см. §3), но отдельный путь XHTTP (для `client-in-*`),
отдельный набор `shortId` и отдельная keypair на каждый inbound —
компрометация одного inbound'а не даёт доступа к остальным на той же ноде.
Self-steal не нужен (в отличие от RU-ноды, ADR-0003) — ноды и так стоят за
границей, ASN↔SNI несоответствие им не грозит.

Добавить/убрать доступ пользователю — заменить его `activeInternalSquads` на
нужный squad из таблицы выше (обычно ровно один content-squad на человека,
без пересечений). Отключить доступ всем разом к конкретной ноде — выключить
её инбаунды в соответствующих squad'ах или сами Host'ы в UI, пропадёт из
подписок сразу у всех участников.
