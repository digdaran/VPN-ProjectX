# Мультивход: прямые подключения ко всем нодам

Как дать клиентам возможность подключаться не только к российской ноде, но и напрямую к зарубежным — и почему это надо делать с открытыми глазами.

---

## Короткий ответ

**Делать — да. Считать равноценной альтернативой — нет.**

Прямое подключение из России к зарубежному VPS упирается в отдельный механизм ограничений (`tcp 16-20`, он же `l4-25`), который к июню-июлю 2026 накрыл Hetzner, OVH, DigitalOcean, Cloudflare, AWS, Oracle — то есть практически все популярные хостинги. Механизм устроен так, что «немного медленнее» не бывает: соединение просто перестаёт передавать данные.

Поэтому правильная модель — не «пять равных входов», а **лестница приоритетов**, где российская нода стоит первой, а зарубежные подхватывают там и тогда, где ограничения слабее либо отсутствуют.

---

## 1. Почему прямой вход за границу — не равноценная замена

### Механизм tcp 16-20 / l4-25

Работает независимо от протокола и порта:

```
Клиент (РФ) ──TCP──▶ Сервер (Hetzner / OVH / DO / AWS …)
                     │
                     ├─ первые ~14–34 КБ в рамках ОДНОГО TCP-соединения проходят
                     │
                     └─ дальше соединение ЗАМОРАЖИВАЕТСЯ
                        RST не приходит; клиент просто ждёт таймаута
```

Ключевые свойства, из-за которых это больно:

| Свойство | Следствие |
|---|---|
| Считаются байты **внутри одного TCP-соединения** | Дробление на HTTP-запросы в том же соединении не помогает |
| Не важно, что за протокол поверх TCP | Reality, WireGuard-over-TCP, голый TCP — всё равно |
| Не важен порт | Перенос на 8443 бесполезен |
| Нет RST, просто заморозка | Клиент видит не ошибку, а зависание — диагностировать тяжелее |
| Порог плавает 14–34 КБ по провайдерам | Иногда «почти работает», иногда мертво — отсюда противоречивые отзывы |

Обойти можно, дробя поток на множество TCP-соединений по ~15 КБ. Арифметика отрезвляет: файл 50 МБ — это около 2500 соединений. Медленно, ресурсоёмко и само по себе выглядит аномально.

### Что важнее: whitelist по SNI **и** CIDR

Более поздние наблюдения сообщества фиксируют переход к белым спискам: связка «разрешённый домен + его CIDR». Подмена SNI не срабатывает, если IP не принадлежит подсети, которая по whois соответствует этому домену.

Формулировка из первоисточника — про случай, когда работает whitelist по CIDR назначения: обход крайне затруднён, и **как правило требуется промежуточный узел с IP из белого списка**.

Это буквально описание вашей схемы. Российская нода с белым IP — не «удобная оптимизация», а единственный надёжный ответ на этот класс ограничений. Прямой вход на Hetzner такой защиты не даёт по определению.

### Вывод

| Путь | Звено 1 (июньский алгоритм) | tcp 16-20 | SNI+CIDR whitelist |
|---|---|---|---|
| Клиент → **RU-нода (белый IP)** → выход | Обрывается на первом шаге ✅ | Не применяется ✅ | Проходит ✅ |
| Клиент → **зарубежная нода** напрямую | Подсеть подозрительная ⚠️ | Применяется ❌ | Не проходит ❌ |

## 2. Тогда зачем это вообще делать

Причины настоящие, просто не те, о которых обычно думают.

| Сценарий | Почему прямой вход нужен |
|---|---|
| **Пользователь за границей** | Отпуск, командировка, релокация. Гнать трафик из Берлина в Москву и обратно — лишние 80–100 мс и бессмысленный крюк |
| **Пользователи в Казахстане** | Если KZ-нода у местного провайдера, для клиентов внутри Казахстана это прямой быстрый вход без российского транзита вообще |
| **RU-нода недоступна** | Плановые работы, авария у хостера, потеря белого статуса. Деградировавший канал лучше, чем никакого |
| **Регионы и операторы со слабым фильтром** | Ограничения внедряются неравномерно; у части пользователей прямой вход работает нормально |
| **Диагностика** | Если у человека не работает RU-вход, но работает прямой — проблема локализована в российском узле, а не в его сети |

Ни одна из этих причин не про «замену RU-ноды». Все — про покрытие ситуаций, где RU-нода не оптимальна или недоступна.

## 3. Рекомендуемая лестница приоритетов

```
┌───────────────────────────────────────────────────────────────┐
│ 1  RU-ВРАТА (белый IP)                              ОСНОВНОЙ  │
│    Клиент → RU → любой из выходов                             │
│    Ломает звено 1, tcp 16-20 не применяется, CIDR проходит    │
└───────────────────────────────────────────────────────────────┘
                            ↓ недоступен
┌───────────────────────────────────────────────────────────────┐
│ 2  РЕЗЕРВНЫЕ RU-ВРАТА (второй провайдер, тоже белый IP)       │
│    Строго лучше любого зарубежного прямого входа              │
└───────────────────────────────────────────────────────────────┘
                            ↓ недоступен
┌───────────────────────────────────────────────────────────────┐
│ 3  ПРЯМОЙ ВХОД НА ЗАРУБЕЖНЫЕ НОДЫ                  РЕЗЕРВ     │
│    KZ → DE → NL → FR  (по возрастанию вероятности блока)      │
│    Работает у части пользователей и всегда — за границей      │
└───────────────────────────────────────────────────────────────┘
```

**Главная практическая рекомендация: второй российский VPS с белым IP окупается лучше, чем возня с прямым зарубежным входом.** Ступень 2 надёжнее ступени 3 при сопоставимой цене.

### Почему KZ выше остальных

Ограничения `tcp 16-20` описаны как нацеленные на подсети зарубежных дата-центров категории Hetzner/OVH/DO/AWS. Казахстанский VPS у местного провайдера в эти списки не обязан попадать. Проверьте свою KZ-подсеть через `dpi-ch` — если она чистая, это ваш лучший зарубежный вход, а заодно самый низкий RTT из перечисленных.

## 4. Влияет ли мультивход на июньский алгоритм ограничений

Опасение резонное: клиент с автовыбором пингует пять серверов — не выглядит ли это как «более 3 параллельных TLS-соединений»?

**Нет, и вот почему.** Счётчик в алгоритме ведётся *к серверу* и *в рамках одного SNI*. Пять разных нод — пять разных IP, то есть пять независимых контекстов. Один пробник на узел не приближает вас к порогу в 3.

Опасен другой паттерн: **много соединений к одному узлу с одним SNI**. Именно от него защищает `xmux.maxConnections: "2-3"`, который уже стоит в конфигах.

Практические правила при включении автовыбора:

| Правило | Зачем |
|---|---|
| Свой SNI-донор (или свой домен) на каждой ноде | Контексты счётчика разведены гарантированно, даже если клиент нестандартный |
| `xmux.maxConnections: "2-3"` на **каждом** профиле | Порог не превышается ни на одном узле |
| Интервал проверки доступности ≥ 15–30 мин, не 3–5 | Меньше фонового шума; на детекцию не влияет, но экономит батарею и трафик |
| Не более 2–3 проб одновременно | Даже при общем SNI-доноре останетесь в пределах порога |
| Предпочитать «упорядоченный перебор» автовыбору по пингу | Ping-тест меряет задержку, а не работоспособность: заморозка tcp 16-20 наступает **после** успешного рукопожатия, и «быстрый» зарубежный узел выиграет тест, а потом зависнет на первом же мегабайте |

Последний пункт важнее остальных. Наивный `url-test` по задержке систематически выбирает **худший** узел: прямой Hetzner отвечает быстрее, чем цепочка через Москву, побеждает в тесте — и умирает на реальной нагрузке. Нужен либо приоритетный список, либо проба с загрузкой заведомо больше 50 КБ.

## 5. Что нужно поменять технически

### 5.1. На зарубежных нодах — публичный inbound

Сейчас у них порт 443 открыт только для российской ноды. Добавляем второй inbound для прямых клиентов:

```bash
# Транзит с RU-ноды остаётся на 443, только для неё
ufw allow from <IP_RU_НОДЫ> to any port 443 proto tcp comment 'transit from RU gate'

# Прямой клиентский вход — отдельный порт, открыт всем
ufw allow 8443/tcp comment 'direct client entry'
```

Разделение по портам, а не общий inbound — сознательное решение:

- транзит и прямой вход считаются раздельно в статистике;
- прямой вход можно выключить одной командой, не трогая основную схему;
- разные `shortId` и пути позволяют понять из логов, каким путём пришёл пользователь.

Готовый конфиг: [`configs/xray-exit-node-public.json`](../configs/xray-exit-node-public.json).

### 5.2. Self-steal на зарубежных нодах — да, но без иллюзий

Заведите поддомены (`de.вашдомен.ru`, `nl.…`, `kz.…`), выпустите сертификаты, поднимите `30-selfsteal.sh`. Это устраняет несоответствие SNI↔ASN и защищает от активного зондирования.

Но честно: **против whitelist по CIDR это не поможет.** Ваш домен не в белом списке цензора, а IP не принадлежит подсети разрешённого домена. Self-steal здесь закрывает слой 3 DPI (зондирование), но не whitelist-механику. Прямой вход остаётся резервом, а не заменой.

### 5.3. Настройки XHTTP против tcp 16-20

Порог считается по байтам внутри одного TCP-соединения. Значит, соединения надо перерабатывать чаще, чем накопится ~14 КБ. В профилях прямого входа:

```json
"xmux": {
  "maxConnections": "2-3",
  "maxConcurrency": 0,
  "cMaxReuseTimes": "8-16",
  "hMaxRequestTimes": "16-32",
  "hMaxReusableSecs": "60-120"
}
```

По сравнению с основным профилем `cMaxReuseTimes` и `hMaxRequestTimes` снижены на порядок — соединения живут меньше и переоткрываются раньше порога.

Это **смягчение, а не решение**. Расплата — заметно больше TCP-хендшейков, выше задержка, ниже потолок скорости. Для мессенджеров и веба терпимо, для видео и больших загрузок — нет.

Из полевых наблюдений сообщества: в отдельных регионах помогает смена транспорта на `httpupgrade` или `grpc`. Имеет смысл держать по одному такому профилю на всякий случай — стоит это одного дополнительного inbound.

### 5.4. В Remnawave

1. **Один сквад со всеми нодами.** Пользователь автоматически существует везде, ничего дублировать не надо.
2. **Порядок хостов.** Remnawave отдаёт хосты в подписке в заданном порядке — поставьте RU-врата первыми. Многие клиенты по умолчанию берут первый рабочий.
3. **Понятные имена.** `RU-Gate (основной)`, `KZ-direct (резерв)`, `DE-direct (резерв)` — человек, у которого что-то не работает, сам переключится осмысленно.
4. **Мгновенное отключение.** Если прямые входы начнут массово подводить — выключаете эти хосты в UI, и они пропадают из подписок у всех.

### 5.5. Автоматическая реакция на падение ноды

Из каталога сообщества: **[Cloudflare Nodes](https://github.com/hteppl/remnawave-cloudflare-nodes)** — управляет DNS-записями Cloudflare по состоянию нод Remnawave. Если RU-врата отвалились, A-запись входного домена переключается на резерв автоматически, без правки подписок.

Дополняет клиентский failover, а не заменяет: DNS решает «куда указывает домен», клиент решает «какой профиль выбрать».

## 6. Маршрутизация: важная деталь

При подключении **напрямую** к зарубежной ноде правило «российские сервисы идут мимо туннеля» перестаёт работать серверной стороной — на DE-ноде нет российского выхода. Банк-клиенты и госуслуги увидят немецкий IP и, скорее всего, заблокируют вход.

Решение уже заложено в `configs/client-example.json` — маршрутизация **на стороне клиента**:

```json
{ "type": "field", "domain": ["geosite:category-ru", "geosite:category-gov-ru"], "outboundTag": "direct" },
{ "type": "field", "ip": ["geoip:ru"], "outboundTag": "direct" }
```

Российские домены и IP идут в обход туннеля вообще, независимо от того, к какой ноде подключён человек. Проследите, чтобы эти правила были во **всех** выдаваемых профилях, а не только в основном.

## 7. Чего ожидать на практике

Честные ожидания, чтобы не удивляться:

| Кто | Что получит |
|---|---|
| Пользователь в РФ, RU-врата работают | Всё отлично, прямые входы не понадобятся |
| Пользователь в РФ, RU-врата упали | Прямой вход: у части заработает нормально, у части — «подключается, но ничего не грузится» (та самая заморозка), у части не заработает вовсе |
| Пользователь в РФ, мобильный интернет | Прямой вход вероятнее всего мёртв: механизм внедрялся в первую очередь на мобильных сетях |
| Пользователь за границей | Прямой вход работает идеально и быстрее, чем через Москву |
| Пользователь в Казахстане | Прямой на KZ-ноду — лучший вариант, проверьте подсеть через `dpi-ch` |

Заранее объясните людям, что резервные профили — именно резервные. Иначе получите поток сообщений «а вот этот сервер не работает», хотя он и не должен был.

## 7.1. Как это сделано в этом проекте (VIP-tier, не только деградация)

Внедрено с одним сознательным отличием от чеклиста ниже: **без** отдельного
self-steal-домена/сертификата на выходную ноду. Вместо этого `client-in-*`
переиспользует тот же classic-Reality донор, что и `transit-in-*` этой же
ноды (свой путь/`shortId`/ключи) — self-steal нужен только RU-ноде (ADR-0003),
а не зарубежным. Это быстрее в развёртывании и не плодит лишние сертификаты
на нодах без реального публичного сайта. Плюс это используется не только как
аварийный «Уровень D» (ADR-0009), а как постоянный параллельный squad
`VIP-Direct` для выбранных пользователей — подробности и обоснование в
ARCHITECTURE.md §10 и ADR-0016.

## 8. Чеклист внедрения

- [ ] Поддомены и A-записи для каждой зарубежной ноды, проксирование Cloudflare выключено
- [ ] `30-selfsteal.sh` на каждой зарубежной ноде (свой домен, свой сертификат)
- [ ] `40-keygen.sh` — отдельные ключи, `shortId` и путь XHTTP для публичного inbound
- [ ] Публичный inbound на порту 8443 из `configs/xray-exit-node-public.json`
- [ ] `ufw allow 8443/tcp` на зарубежных нодах; порт 443 по-прежнему только с RU-ноды
- [ ] Все ноды в одном скваде Remnawave
- [ ] Порядок хостов: RU-врата первыми; понятные имена с пометкой «резерв»
- [ ] Клиентские правила маршрутизации `geosite:category-ru → direct` во **всех** профилях
- [ ] `xmux` с укороченным временем жизни соединений в резервных профилях
- [ ] Прогнать `dpi-ch` по подсетям всех зарубежных нод, KZ — в первую очередь
- [ ] Проверить с российского домашнего и мобильного интернета: скачать файл >5 МБ через каждый прямой вход
- [ ] Предупредить пользователей, что резервные профили — резервные

Последний пункт проверки — самый показательный. Рукопожатие пройдёт везде; ограничение проявляется только на объёме. Тест «подключился, страничка открылась» ничего не доказывает.
