# Сравнение панелей управления Xray

Развёрнутое обоснование выбора. Актуально на июль 2026.

---

## Кандидаты

| Проект | Что это | Статус |
|---|---|---|
| **3x-ui** (MHSanaei) | Монолит на Go: веб-панель и Xray-core в одном процессе | Активно развивается |
| **Marzban** (Gozargah) | Панель + ноды, Python/FastAPI | Разработка практически остановилась |
| **Marzneshin** | Форк Marzban с переработанной архитектурой нод | Живой, но экосистема меньше |
| **Remnawave** | Панель (NestJS + React) + ноды (Remnanode), микросервисы, Postgres | Активно развивается, один мейнтейнер |

## Ключевое различие: модель пользователя

Это тот пункт, который в вашем случае решает всё.

### 3x-ui: пользователь привязан к inbound на конкретном сервере

```
Сервер RU  →  3x-ui #1  →  inbound  →  [Иван] [Пётр] [Анна]
Сервер FR  →  3x-ui #2  →  inbound  →  [Иван] [Пётр] [Анна]   ← создавать заново
Сервер DE  →  3x-ui #3  →  inbound  →  [Иван] [Пётр] [Анна]   ← создавать заново
Сервер NL  →  3x-ui #4  →  inbound  →  [Иван] [Пётр] [Анна]   ← создавать заново
Сервер KZ  →  3x-ui #5  →  inbound  →  [Иван] [Пётр] [Анна]   ← создавать заново
```

Цена операций при 100 пользователях и 5 серверах:

| Операция | Действий |
|---|---|
| Добавить одного человека | 5 |
| Удалить одного человека | 5 |
| Продлить всем подписку | 500 |
| Ротация ключей после утечки | 500 |
| Сверка «кто где есть» | 5 выгрузок + ручная диффка |

Без оркестратора это неуправляемо. С оркестратором (`api/xui_orchestrator.py`) — управляемо, но вы становитесь автором и сопровождающим распределённой системы с проблемой согласованности: если одна панель была недоступна в момент массовой операции, состояние разошлось, и узнать об этом можно только сверкой.

### Remnawave: пользователь → сквад → множество нод

```
                       ┌─ нода FR ─┐
[Иван] ─→ сквад «EU» ──┼─ нода DE ─┤
                       └─ нода NL ─┘

[Пётр] ─→ сквад «Все» ─→ FR + DE + NL + KZ + RU
```

| Операция | Действий |
|---|---|
| Добавить одного человека | 1 |
| Удалить одного человека | 1 |
| Продлить всем подписку | 1 запрос в цикле, но состояние консистентно |
| Ротация ключа одного человека | 1 (`revoke`) |
| Смена страны выхода для группы | 1 (переназначить сквад) |

Разница не в удобстве, а в классе задачи. В первом случае вы пишете и отлаживаете распределённую систему; во втором — вызываете один HTTP-метод.

## Разбор по критериям вашей задачи

### 1. 5 серверов, 10–100 пользователей

**Remnawave** — единственный вариант, где это не превращается в рутину. 3x-ui потребует оркестратора, Marzban мёртв, Marzneshin справится, но с меньшим комфортом.

### 2. Управление через API / самописный сервис

| | Качество API |
|---|---|
| Remnawave | OpenAPI-спека, TS SDK, вебхуки по юзерам и нодам, API-ключи через UI |
| Marzneshin | REST есть, документирован скромнее |
| Marzban | REST есть, но проект не развивается |
| 3x-ui | API есть, но он про один узел; мультисерверность вы пишете сами |

Для «самописного, а может есть уже и готовые» — у Remnawave есть каталог `awesome-remnawave` с ботами, биллингами, панелями статистики и автобэкапами от сообщества. Стоит посмотреть до того, как писать своё: скорее всего, ваш сценарий уже реализован.

### 3. Разделение управляющего и транзитного контуров

**Критично именно из-за российской ноды.** Панель должна стоять вне РФ, а на российском VPS — только Remnanode без базы пользователей.

- Remnawave: панель и ноды разделены изначально. ✅
- Marzban/Marzneshin: разделены. ✅
- 3x-ui: панель = узел. На каждом сервере полноценная панель с БД, в том числе на российском. ❌

Это не теоретическое соображение: если российский сервер изымут или он окажется скомпрометирован, в случае 3x-ui вместе с ним уходит вся база пользователей этого узла.

### 4. Отказоустойчивость

Remnawave: ноды продолжают обслуживать клиентов при падении панели. Marzban — нет (нода останавливается). Для раздачи знакомым это разница между «я чиню панель в спокойном режиме» и «мне пишут 40 человек».

## Честные минусы Remnawave

Стоит знать до, а не после.

| Минус | Насколько существенно | Что делать |
|---|---|---|
| **Один мейнтейнер** | Существенно. Проект может остановиться | Держать бэкапы БД; уметь поднять голый Xray без панели — конфиги для этого в `configs/` |
| 2 ГБ RAM на панель | Умеренно | Отдельный дешёвый VPS под панель |
| Нет мульти-админа | Слабо для вашего кейса | Если админов несколько — только общий доступ |
| Нет статуса On Hold | Слабо | Эмулируется через `disable` + `expireAt` |
| Mux не в UI хостов | Умеренно | Задаётся через сырой конфиг ядра — в `configs/` уже так и сделано |
| Документация только на английском | Слабо | — |
| Нет WireGuard/VMess-хостов из коробки | Слабо | VMess устарел, WG отдельным контуром (план Б) |

## Когда правильный ответ — 3x-ui

Не отбрасывайте вариант из принципа. 3x-ui уместен, если:

- серверов остаётся ≤ 2 и рост не планируется;
- пользователей ≤ 15;
- вы хотите видеть и понимать каждый компонент, и автоматизация вторична;
- нужен минимум ресурсов (панель на VPS с 512 МБ RAM);
- нужен мульти-админ.

При таком выборе возьмите `api/xui_orchestrator.py` как основу и обязательно реализуйте регулярный `reconcile()` — без сверки состояния распределённая ручная схема расходится в течение недель.

## Миграция

Если начнёте с 3x-ui и захотите перейти:

| Откуда | Куда | Как |
|---|---|---|
| Marzban | Remnawave | Официальный гайд миграции в документации |
| 3x-ui | Remnawave | Готового инструмента нет. Выгрузить клиентов через API 3x-ui, создать через API Remnawave. При сохранении UUID и параметров inbound клиенты **не заметят перехода** |
| Любая | Голый Xray | Конфиги в `configs/` — рабочие без панели вообще |

Последняя строка — не запасной вариант на бумаге, а реальная страховка. Панель управляет конфигурацией; трафик носит Xray. Если панель по любой причине станет недоступна, у вас на руках остаются рабочие конфиги.

## Итог

**Для вашей схемы (RU-вход + 4 зарубежных выхода, 10–100 пользователей, управление через API) — Remnawave.**

Решающие аргументы, по убыванию веса:

1. Модель «пользователь → сквад → много нод» соответствует задаче один в один.
2. Панель физически отделена от нод, база пользователей не лежит на российском VPS.
3. API-first: спека, SDK, вебхуки, готовая экосистема сообщества.
4. HWID-лимит — единственная реальная защита от расползания ключей, что напрямую бережёт репутацию белого IP.
5. Ноды переживают падение панели.

Главный риск — один мейнтейнер. Он митигируется бэкапами и наличием рабочих конфигов для голого Xray.
