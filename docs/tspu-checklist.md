# Чеклист TSPU-стойкости и методика проверки

Практический документ: что проверить перед запуском, чем измерить, что делать при срабатывании.

---

## Часть 1. Чеклист перед запуском

Проходите сверху вниз. Пункты со знаком 🔴 — блокирующие, без них запускаться нельзя.

### Звено 1 — IP и подсеть

| | Пункт | Как проверить |
|---|---|---|
| 🔴 | RU-VPS имеет IP из белых списков и не в «подозрительной» AS | Прогнать `dpi-ch` из проекта [dpi-checkers](https://github.com/hyperion-cs/dpi-checkers), вкладка **Russian Infrastructure Providers**, колонка **Siberian** |
| 🔴 | Клиенты подключаются к **домену**, а не к сырому IP | Открыть выданную ссылку подписки, проверить поле `address` |
| ⚪ | Заготовлен резервный RU-VPS у другого провайдера | Второй домен + сертификат уже выпущены |
| ⚪ | Проверены подсети всех зарубежных нод | `dpi-ch`, вкладка **Foreign Infrastructure Providers** — там же смотрим `tcp 16-20` |

Важно: белый IP защищает только пока он белый. Проверяйте его **еженедельно** — реестры меняются, и узнать о выпадении из белого списка постфактум по жалобам пользователей неприятно.

### Звено 2 — фингерпринт

| | Пункт | Как проверить |
|---|---|---|
| 🔴 | `fingerprint` = `firefox` (НЕ `chrome`, НЕ `safari`, НЕ `ios`) | `grep -r fingerprint` по всем клиентским профилям |
| 🔴 | Ни в одном профиле нет `fingerprint: "random"` | Непредсказуемость здесь — не преимущество: можно случайно попасть в чёрный список |
| ⚪ | Подготовлен резервный профиль с `fp=edge` | Лежит в подписке как отдельный хост |
| ⚪ | Клиенты обновлены до версий с поддержкой `xhttp extra` | Старые сборки молча игнорируют `extra` |

### Звено 3 — параллельные соединения

| | Пункт | Как проверить |
|---|---|---|
| 🔴 | В клиентском конфиге задан `xmux.maxConnections: "2-3"` | Проверить в выданной ссылке параметр `extra` |
| 🔴 | `xmux.maxConcurrency` = `0` | Одновременно с `maxConnections` он не работает — будет игнор обоих |
| 🔴 | На транзитных outbound'ах RU-ноды тоже задан `xmux` | Трансграничный стык проверяется отдельно |
| ⚪ | Настроено ≥2 `shortId` | Смена `shortId`+пути даёт запасной профиль без переустановки |

### Активное зондирование (слой 3 DPI)

| | Пункт | Как проверить |
|---|---|---|
| 🔴 | Self-steal на RU-ноде работает | `curl -sSI https://vpn.вашдомен.ru/` **с внешнего хоста** → нормальный HTTP-ответ |
| 🔴 | A-запись домена указывает ровно на IP RU-ноды | `dig +short A vpn.вашдомен.ru` |
| 🔴 | Проксирование Cloudflare для этого домена **выключено** | Reality несовместим с проксированием |
| 🔴 | Сертификат валиден и CN совпадает с доменом | `openssl s_client -servername ... -connect ...:443` |
| ⚪ | Контент сайта уникален, а не шаблон из скрипта | Одинаковый контент на разных IP — сама по себе сигнатура |
| 🔴 | На выходной ноде `serverNames`/`dest`/`xhttpSettings.host`+`path` инбаунда `transit-in` дословно совпадают со «своим» `out-*` в `xray-transit-outbound.json` | `scripts/50-preflight.sh xray-transit-outbound.json xray-exit-node.json` (или `-public.json`) — сверяет автоматически. Частая ошибка: скопировали шаблон `xray-exit-node.json` (значения под DE) на FR/NL/KZ-ноду и забыли поменять SNI-донор — по отдельности оба файла валидны, Reality-рукопожатие между RU-нодой и этим выходом просто не установится |

### Поведенческий анализ (слой 4 DPI)

| | Пункт | Как проверить |
|---|---|---|
| 🔴 | Транспорт = `xhttp`, не `tcp` и не `ws` | WebSocket детектируется давно и надёжно |
| 🔴 | Задан `xPaddingBytes: "100-1000"` | И на сервере, и на клиенте |
| ⚪ | Версии Xray на всех нодах совпадают | `scripts/90-healthcheck.sh` проверяет автоматически |
| ⚪ | Версия Xray на клиентах совпадает с серверной | XHTTP в активной разработке; рассинхрон = молчаливые сбои |

### Гигиена белого IP

| | Пункт | Как проверить |
|---|---|---|
| 🔴 | Торренты заблокированы в routing | Правило `protocol: bittorrent → block` |
| 🔴 | Исходящий SMTP (25/465/587) заблокирован | `ufw status \| grep 25` |
| 🔴 | `geoip:private` заблокирован | Иначе через вас ходят во внутреннюю сеть хостера |
| 🔴 | Панель и БД **не** на российском VPS | — |
| ⚪ | Задан HWID-лимит устройств (3–5) | В настройках пользователя Remnawave |
| ⚪ | Задан лимит трафика на пользователя | Даже щедрый — отсекает аномалии |
| ⚪ | Порт ноды (2222) закрыт от интернета | `ufw status` — должно быть только с IP панели |

## Часть 2. Методика проверки

### 2.1. Воспроизведение алгоритма ограничений

Оригинальный тестовый стенд из исследования — на macOS с Chrome. Ниже адаптация под Linux, curl и любой хост.

```bash
#!/usr/bin/env bash
# Проверяет, применяется ли ограничение по числу параллельных TLS
# к вашей подсети. Запускать ИЗ РОССИИ, с домашнего или мобильного
# провайдера — не с сервера.

TARGET_IP="ВАШ_RU_IP"
SNI="test-$(date +%s).example.com"   # уникальный SNI обнуляет контекст цензора
COUNT=5                              # порог — 3; берём с запасом

echo "Проверяю $COUNT параллельных TLS к $TARGET_IP (SNI: $SNI)"

for i in $(seq 1 $COUNT); do
  (
    out=$(curl -sS -o /dev/null -w '%{http_code} %{time_connect} %{time_appconnect}' \
      --max-time 15 \
      --resolve "$SNI:443:$TARGET_IP" \
      "https://$SNI/" 2>&1)
    echo "  conn $i: $out"
  ) &
done
wait

echo
echo "Интерпретация:"
echo "  time_appconnect > 0 у всех  → TLS проходит, ограничение НЕ применяется"
echo "  time_appconnect = 0, time_connect > 0 → TCP есть, TLS заморожен: ВЫ ПОД ОГРАНИЧЕНИЕМ"
echo "  всё по нулям → сетевая проблема, не DPI"
```

Ключевая диагностическая деталь: при срабатывании ограничения **TCP-соединение устанавливается всегда**, замораживается именно TLS. Если `time_connect` ненулевой, а `time_appconnect` — нулевой, вы поймали заморозку.

Повторный запуск делайте **не раньше чем через 120 секунд** и с новым SNI, иначе измеряете остаточную заморозку, а не новый эксперимент.

### 2.2. Проверка активного зондирования

С хоста **вне** вашей инфраструктуры:

```bash
DOMAIN="vpn.вашдомен.ru"

# 1. Обычный запрос — должен вернуться настоящий сайт
curl -sSI "https://$DOMAIN/" | head -20

# 2. Сертификат: издатель, субъект, срок
echo | openssl s_client -servername "$DOMAIN" -connect "$DOMAIN:443" 2>/dev/null \
  | openssl x509 -noout -issuer -subject -dates

# 3. Соответствие DNS и реального адреса
dig +short A "$DOMAIN" @1.1.1.1

# 4. Поведение при нестандартных запросах — настоящий сервер не должен рвать соединение
curl -sS -o /dev/null -w '%{http_code}\n' "https://$DOMAIN/nonexistent-path-$(date +%s)"
curl -sS -o /dev/null -w '%{http_code}\n' --http1.1 "https://$DOMAIN/"
```

Что должно получиться: `200`/`301` на корень, валидный Let's Encrypt сертификат с CN = вашему домену, `404` на несуществующий путь. Любая TLS-ошибка или обрыв — self-steal собран неправильно.

### 2.3. Проверка фингерпринта

```bash
# Через ваш прокси (SOCKS на 10808 из client-example.json)
curl -sS --socks5-hostname 127.0.0.1:10808 \
  https://tls.peet.ws/api/all | jq '{ja3: .tls.ja3_hash, ja4: .tls.ja4, peetprint: .tls.peetprint_hash}'

# Напрямую из настоящего Firefox — сравните хэши
```

Хэши должны совпадать с настоящим Firefox. Если отличаются — либо клиент не поддерживает `fingerprint`, либо параметр не применился.

### 2.4. Проверка числа параллельных соединений

На RU-ноде, во время активной работы клиента:

```bash
# Сколько TLS-сессий держит один клиентский IP
ss -tn state established '( dport = :443 or sport = :443 )' \
  | awk '{print $5}' | cut -d: -f1 | sort | uniq -c | sort -rn | head

# Должно быть ≤3 на IP. Если больше — xmux не применился.
```

Это самая частая ошибка: `extra` прописан в серверном конфиге, но клиент его игнорирует (старая сборка), и защита звена 3 не работает при внешне корректном конфиге.

### 2.5. Проверка поведенческого профиля

Раз в пару недель:

```bash
# Соотношение входящего и исходящего трафика на интерфейсе
vnstat -i eth0 -m

# У настоящего веб-сервера исходящий сильно превышает входящий.
# Примерное равенство — аномалия для заявленного «сайта».
```

При self-steal это менее критично (сайт-то настоящий), но за метрикой стоит следить: резкая смена профиля обычно означает, что кто-то начал качать через вас что-то объёмное.

## Часть 3. Диагностика по симптомам

| Симптом | Наиболее вероятная причина | Что делать |
|---|---|---|
| Работает 30–60 сек, потом виснет, через 2 мин снова работает | Звено 3: заморозка 120 сек | Проверить `xmux.maxConnections` на клиенте. Скорее всего клиент игнорирует `extra` |
| Перестало работать полностью и сразу у всех | IP или подсеть попали под ограничение | Прогнать `dpi-ch`. Эвакуация на резервный VPS |
| После смены настроек на клиенте не работает 10 минут | Блокировка 600 сек за смену фингерпринта во время заморозки | Просто подождать. Не дёргать настройки дальше |
| Не работает у одного оператора, работает у другого | Региональные различия политик ТСПУ | Нормально. Дать пользователю профиль с другим `fp` |
| Работает на мобильном, не работает на домашнем (или наоборот) | То же самое | То же самое |
| Соединение есть, но скорость 100 кбит/с | Не ограничение, а шейпинг или проблема транзита | Проверить `observatory`, RTT до выходных нод |
| Клиент подключился, но сайты не открываются | Ошибка в routing или DNS | Проверить правила `geosite`, обновить geo-базы |
| После обновления Xray на сервере всё сломалось | Рассинхрон версий сервер/клиент | Откатить сервер либо обновить клиентов. XHTTP чувствителен к версиям |

## Часть 4. Порядок действий при массовом сбое

1. **Не менять ничего на клиентах в первые 5 минут.** Смена фингерпринта во время активной заморозки даёт блокировку на 600 секунд вместо 120 — вы сделаете хуже.
2. **Определить масштаб.** Один пользователь, один оператор, один регион или все сразу? Это сразу отсекает половину гипотез.
3. **Проверить инфраструктуру:** `scripts/90-healthcheck.sh`. Ноды живы? Сертификат валиден? Self-steal отвечает?
4. **Проверить подсеть:** `dpi-ch` по вашему IP.
5. **Если инфраструктура жива, а подсеть чистая** — вероятно, изменились параметры алгоритма. Переключить пользователей на резервный профиль (другой `fp`, другой `shortId`).
6. **Если подсеть попала под ограничение** — эвакуация: сменить A-запись на резервный VPS. В Remnawave — выключить старый хост, включить резервный; клиенты подхватят при обновлении подписки.
7. **Разбор постфактум.** Записать, что именно сработало: без этого следующая волна застанет так же врасплох.

## Часть 5. Что менять НЕ надо

Частые ошибки, которые не помогают, а иногда вредят:

- **Переносить на нестандартный порт.** Ограничение не зависит от порта. Вы просто усложните себе жизнь.
- **Переходить на TLS 1.2.** Оба подвержены. Плюс поменяете фингерпринт в непредсказуемую сторону.
- **Ставить `fingerprint: "random"`.** Можно случайно попасть в чёрный список, причём непредсказуемо и невоспроизводимо.
- **Отключать HTTP/2 в браузере.** Изменит фингерпринт — и не в лучшую сторону.
- **Менять SNI-донор на apple.com / icloud.com.** Apple держит IP в собственных ASN; несоответствие с вашим хостингом видно сразу.
- **Использовать мелкий малопосещаемый сайт как SNI-донор.** По той же причине: трафик к нему аномален.
- **Возвращаться на WebSocket.** Детектируется давно и надёжно по паттерну постоянного двунаправленного потока.
- **Обновлять Xray на всех нодах разом.** Сначала одна, сутки наблюдения, потом остальные.

## Часть 6. За чем следить дальше

Ситуация меняется; параметры, описанные здесь, актуальны на июль 2026 и почти наверняка изменятся.

| Источник | Что там |
|---|---|
| [XTLS/Xray-core Issues](https://github.com/XTLS/Xray-core/issues) | Апстрим-обсуждения блокировок в реальном времени |
| [net4people/bbs](https://github.com/net4people/bbs/issues) | Международное сообщество по обходу цензуры, технический разбор |
| [dpi-checkers](https://github.com/hyperion-cs/dpi-checkers) | Инструмент проверки подсетей; обновляется под новые виды ограничений |
| Хабр, хабы «Сетевые технологии» / «Информационная безопасность» | Разборы новых волн на русском |

Отдельно отмечу: в исследовании июня 2026 автор допускает, что параметры ограничений впоследствии смягчат — похожее уже наблюдалось в конце 2025 года. Не стройте архитектуру под один конкретный набор порогов; стройте так, чтобы ломать цепочку в нескольких местах одновременно.
